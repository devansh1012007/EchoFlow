### 1.3 Routing Model

The frontend does **not** use React Router. It uses **tab-based state rendering** inside `App.tsx`'s `MainContent` component:

- `activeTab` state holds the current view (`"feed"`, `"explore"`, `"upload"`, `"inbox"`, `"profile"`)
- `MainContent` renders the corresponding page component conditionally
- Auth gate: `if (!isAuthenticated && !isLoading) return <LoginPage />` — this short-circuits the entire app shell when unauthenticated
- This is a single-page app (SPA) architecture served by Express

### 1.4 Backend Contract

The frontend consumes a mock Express backend (`server.ts`) on port 3001 that:
- Serves Vite assets (dev) / static `dist/` (prod) as middleware
- Exposes REST API endpoints for auth, feed, clips, interactions, comments, sharing, profiles
- Generates synthetic WAV audio on-the-fly for `/api/media/audio/:clip_id.wav`
- Uses JWT-like tokens with base64-encoded payloads (not RFC-compliant JWTs — see §5.1)

## 2. Authentication & JWT Implementation

### 2.1 Storage Strategy

| Token | Storage | Key |
|---|---|---|
| Access token | `sessionStorage` | `ef_access_token` |
| Refresh token | `sessionStorage` | `ef_refresh_token` |
| User object | `sessionStorage` | `ef_user` |

**Decision rationale:** `sessionStorage` is used instead of `localStorage`, meaning tokens do not persist across browser restarts/tabs. This reduces the window of opportunity for token theft via XSS (tokens are cleared when the tab closes).

### 2.2 API Client (`api/client.ts`)

The `apiRequest` function implements:

1. **Automatic auth header injection** — reads `ef_access_token` from sessionStorage, sets `Authorization: Bearer <token>`
2. **401 interceptor with single-flight refresh** — on 401, calls `refreshAccessToken()` which:
   - Uses a `refreshPromise` mutex to deduplicate concurrent refresh attempts
   - POSTs to `/auth/token/refresh/` with the refresh token
   - Stores the rotated refresh token (if returned) and new access token
   - Retries the original request with the new access token
3. **Session expiry broadcast** — if refresh fails, dispatches `ef_session_expired` CustomEvent
4. **FormData handling** — skips `Content-Type` header for FormData (lets browser set multipart boundary)
5. **Error normalization** — extracts `detail`, `error`, or field-level errors from response body

### 2.3 Auth Store (`stores/auth.tsx`)

The `AuthProvider` manages:
- `user` (from sessionStorage on init)
- `profile` (fetched via `/profile/me/` on mount if tokens exist)
- `isAuthenticated` (derived from `!!user`)
- `isLoading` (true until initial profile fetch completes or fails)
- `login()`, `register()`, `logout()` lifecycle methods

**Key behaviors:**
- `register()` calls register endpoint, then login endpoint (to obtain tokens), then sets `ef_new_user` flag, then refreshes profile
- `logout()` calls `/auth/logout/` (best-effort), then clears local state
- `ef_session_expired` event clears all tokens and user state

### 2.4 Login Page (`pages/Login.tsx`)

The login page is a full-screen route with:
- Login/register mode toggle
- Username + password (login) or email + username + password (register)
- Show/hide password toggle
- Error message display with field-level error extraction
- Uses `useAuth().login()` and `useAuth().register()` which call the JWT API

## 3. Player & Media Architecture

### 3.1 Audio Player Store

The `PlayerProvider` (`stores/player.tsx`) manages:
- HLS.js instance lifecycle (create, loadSource, attachMedia, destroy)
- HTML5 Audio element lifecycle
- Synthetic frequency visualizer (24 bars via `requestAnimationFrame`)
- Playback telemetry (heartbeat every 6s, final telemetry on pause/end)
- Auto-advance on 99% completion
- Skip forward/backward (10s default)
- Playback rate control (1x → 1.25x → 1.5x → 2x cycle)
- Hands-free mode flag

### 3.2 Telemetry Pipeline

| Event | Trigger | Payload |
|---|---|---|
| View heartbeat | `timeupdate` every ~6s | `{ action_type: "view", watch_time_ms }` |
| View on pause | `pause` event | `{ action_type: "view", watch_time_ms }` |
| View on end | `ended` event → auto-advance | `{ action_type: "view", watch_time_ms }` |
| Skip | Manual nextClip before 90% completion | `{ action_type: "skip", listen_duration_ms, reel_position_ms, reel_id }` |

### 3.3 Issues Identified

- **Telemetry on pause fires unconditionally** — even on the very first pause (line 85-90 of player.tsx), sending `watch_time_ms` of 0 if `audio.currentTime` hasn't updated. The `audio.currentTime > 0` guard mitigates but doesn't prevent near-zero values.
- **No `ended` event telemetry deduplication** — on natural completion, both `timeupdate` (99% threshold) and `ended` fire; `handleAutoAdvance` is called twice. The second call hits `nextClip("auto")` with a stale `currentClip` (already advanced).
- **HLS.js error handling is shallow** — fatal errors are logged but not recovered (no retry, no fallback to native audio).

## 5. Security Analysis

### 5.1 JWT Token Format

**CRITICAL:** The mock backend (`server.ts`) generates JWT-like tokens with the format `eyJ<hash>.<base64payload>.dummy_sig_<timestamp>`. This is **not** a standards-compliant JWT:
- Uses `.dummy_sig_<timestamp>` as the signature (not a cryptographic signature)
- The payload is a bare base64-encoded JSON with `user_id`, `username`, and `exp` claims
- The frontend treats it as a bearer token (correct usage) but the backend's `getAuthUser` decodes it via `Buffer.from(token.split(".")[1], "base64")`

**Impact if deployed to production:** Tokens can be forged by any client since there is no cryptographic signature verification. The real Django backend (per AGENTS.md) uses `dj-rest-auth` with proper JWT signing — the mock server is dev-only.

### 5.2 Token Storage

Using `sessionStorage` is a reasonable security tradeoff for a dev/test environment. In production:
- `sessionStorage` is still vulnerable to XSS (any JS can read it)
- Consider HttpOnly cookies with `SameSite=Strict` for production-grade token storage
- The current approach is acceptable for the mock environment

### 5.3 Input Validation

- **Comment text**: The mock server enforces `text.trim().substring(0, 500)` but the frontend CommentSheet doesn't limit input length — a user could type a very long comment that gets silently truncated.
- **Upload title**: Limited to 255 chars via `maxLength` on the input (correct)
- **Register form**: Username/password length not validated client-side (only server-side in mock)

### 5.4 Error Information Disclosure

- Auth errors surface raw server messages to the user (`err?.data?.non_field_errors?.[0]` etc.) — this is appropriate for dev but in production, generic error messages are safer.
- `console.warn` calls throughout for failed API calls — these are visible in dev tools only, acceptable.

## 6. Performance Analysis

### 6.1 Bundle

- Main bundle: React 19 + hls.js + lucide-react + player logic — reasonable for a media SPA
- `motion` package (v12.23) is in `dependencies` but **not imported anywhere** in `src/` — dead dependency adding ~2-5MB to the bundle. Should be removed.
- `@google/genai` is in `dependencies` but **not imported anywhere** in `src/` — dead dependency.
- `@types/express`, `@types/multer` are devDependencies correctly used by `server.ts`.

### 6.2 Renders

- `ReelCard` receives `currentClip`, `isPlaying`, `progress`, `currentTime`, `duration`, `seek`, etc. from the PlayerContext — any player state change causes all visible ReelCards to re-render. With only one card visible (feed mode), this is acceptable.
- The analyzer visualizer (`audioFrequencies`) updates every animation frame (60fps) and triggers re-renders of all components consuming `usePlayer()` — this is the most frequent state mutation in the app and could cause frame drops if the component tree is deep.
- `useEffect` in player.tsx depends on `[currentClip]` (line 112) — this recreates all audio event listeners whenever the clip changes, which is correct but means the visualizer interval restarts too.

### 6.3 Data Fetching

- No client-side caching layer (e.g., React Query, SWR) — each page re-fetches data on mount. The mock server is fast (in-memory) so this is tolerable for dev but would cause unnecessary network load against a real backend.
- FeedPage's `loadFeed` is recreated on every `currentClip` change due to the dependency array, causing potential redundant fetches.

## 8. Type System Health

### 8.1 TypeScript Configuration

- `tsconfig.json` uses `"jsx": "react-jsx"` (React 19 automatic runtime)
- `skipLibCheck: true` — skips type checking of node_modules, acceptable
- `strict` is NOT explicitly enabled — **the compiler does not run in strict mode** because `"strict"` is absent from `compilerOptions`. This means null checks, implicit `any`, and strict function types are not enforced.

**SECURITY IMPLICATION:** Without strict null checks, runtime `null`/`undefined` access errors are not caught at compile time. This is particularly risky in `ReelCard` where `clip.creator_name[0]?.toUpperCase()` could fail if `creator_name` is an empty string.

### 8.2 Type Coverage

- `api/client.ts`: Well-typed with generics per endpoint method
- `types/echoflow.ts`: All API contracts are typed (`FeedClip`, `User`, `OwnProfile`, `PublicProfile`, `Comment`, `ShareEvent`, `FeedResponse`, `CursorPaginated<T>`, `AuthTokens`)
- `stores/auth.tsx`: Context type is fully specified
- `stores/player.tsx`: Context type is fully specified
- **Gap**: `apiRequest<T = any>` defaults to `any` — the generic is optional and untyped if omitted. This is acceptable for the `logout` void endpoint but masks errors in ad-hoc calls.

### 8.3 Type Errors (Pre-existing)

Running `tsc --noEmit` produces errors ONLY in `sample_frontend2/` (a separate sample project), not in `src/`. The main `src/` tree compiles cleanly.

## 12. Bugs Identified

### 12.1 Critical

1. **Dead `AuthModal` component** — removed from `App.tsx` but the file still exists at `components/auth/AuthModal.tsx`. Should be deleted to prevent confusion and reduce bundle size (if tree-shaking doesn't eliminate it).

2. **Unused `motion` and `@google/genai` dependencies** — add unnecessary weight to the build. `motion` is particularly large.

### 12.2 High

3. **Follow button state resets on re-render** (`ReelCard.tsx:56`) — `useState<boolean>(false)` for `isFollowing` is never initialized from any backend state. The toggle works optimistically but resets to "not following" if the card re-renders (e.g., on player progress update).

4. **Comment delete UI missing** — `handleDeleteComment` is defined (line 62) but no UI element calls it. The delete functionality is dead.

5. **No `strict` mode in tsconfig** — null-safety is not enforced at compile time, risking runtime crashes on null access.

### 12.3 Medium

6. **HLS.js error recovery is minimal** — fatal errors destroy the instance but don't attempt retry or fallback. The old_frontend had `hls.startLoad()` retry on network errors.

7. **`onloadedmetadata` async leak** — if a file is replaced before metadata loads, the `URL.revokeObjectURL` call inside the callback is skipped, leaking the object URL. The `onloadedmetadata` callback also references potentially stale state.

8. **System status hardcoded** — Header always shows "Workers Active" regardless of `/health/` endpoint state.

9. **Telemetry double-fire on completion** — `handleAutoAdvance` called from both `timeupdate` (99% threshold) and `ended` events.

10. **`loadFeed` dependency churn** — `useCallback` deps include `currentClip`, `playClip`, `setQueue` which are not stable, causing unnecessary re-creation of `loadFeed` and potential redundant fetches.

### 12.4 Low

11. **Unused imports**: `Disc3` (`Feed.tsx`), `Radio` (`Login.tsx`), `Activity` (`Header.tsx`)

12. **`UserIcon` named import inconsistency** — imported as `User as UserIcon` in Profile.tsx but `User` elsewhere

13. **No error boundary** — API failures in deeply nested components could crash the entire app without a fallback UI.

14. **`console.warn` in production code paths** — the `catch` blocks in several components (`CommentSheet`, `ReelCard`) write to console; these should be gated behind a dev flag or use a proper logging layer.

## 13. Recommendations

### 13.1 Immediate (P0)

1. **Delete dead `AuthModal` component** (`components/auth/AuthModal.tsx`) — replaced by LoginPage, no longer imported anywhere.
2. **Remove unused dependencies** (`motion`, `@google/genai`) from `package.json` — reduces bundle size.
3. **Fix follow button state** in `ReelCard` — initialize from `clip.creator_is_following` if the backend provides it, or at minimum don't reset on re-render.
4. **Enable TypeScript strict mode** in `tsconfig.json` (`"strict": true`) — catches null-safety issues at compile time.

### 13.2 Short-term (P1)

5. **Add comment delete UI** — wire up `handleDeleteComment` with a visible delete button for comment authors.
6. **Implement HLS.js error recovery** — add `hls.startLoad()` retry on network errors, fallback to native audio on fatal errors.
7. **Add error boundaries** — wrap root app and major route components in error boundaries to prevent full-app crashes.
8. **Fix object URL leak** in UploadPage — use a `useEffect` cleanup or a ref to track and revoke the URL.

### 13.3 Medium-term (P2)

9. **Add client-side data caching** — use a lightweight cache (e.g., SWR or React Query) to avoid redundant refetches when navigating between tabs.
10. **Implement system status polling** — connect the Header's status indicator to `/health/` endpoint and reflect real state.
11. **Add `aria-live` regions** for error messages and async status updates.
12. **Implement comment reply threading** — fetch and display nested replies when `reply_count > 0`.

### 13.4 Long-term (P3)

13. **Migrate to HttpOnly cookies** for JWT storage in production — prevents XSS-based token theft. The current sessionStorage approach is acceptable for the dev mock server.
14. **Add focus-visible indicators** — replace `focus:outline-none` with `focus-visible:` variants for keyboard navigation.
15. **Replace hardcoded default peers** in ShareModal with a real "frequent contacts" API or user search history.

## 14. Compliance Notes

### 14.1 JWT Auth Reference

The JWT auth implementation follows the same pattern as the old_frontend (`old_frontend/main.jsx`):
- Access + refresh token pair stored in browser storage
- 401 interceptor with automatic refresh rotation
- Single-flight mutex to prevent multiple concurrent refresh requests
- Session expiry broadcast via CustomEvent

**Improvement over old_frontend:** The current implementation uses `sessionStorage` (cleared on tab close) vs. old_frontend's `localStorage` (persists indefinitely). The current also implements single-flight refresh deduplication, which the old_frontend lacked (concurrent 401s would trigger multiple refresh requests).
